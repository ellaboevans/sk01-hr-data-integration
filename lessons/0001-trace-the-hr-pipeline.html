Lesson 0001 · Code review readiness

Trace one employee from raw file to golden row

If you can narrate one record's journey, you understand the repository's architecture. This lesson builds that narrative in seven stages.

15–20 minutes

Before the code: identify the grain

The pipeline does not start with four equivalent employee tables. It starts with two identity sources and two event/enrichment sources.

Identity sourcesGlobalTech HRIS and AcquiredCo HRIS are allowed to create golden employees.
Enrichment sourcesPayroll and benefits can add facts to an existing identity, but cannot create one.
Why this matters: a payroll record without an HRIS match may be a stale ID, integration error, or “ghost employee.” Treating it as a real identity would hide the anomaly.

The complete route

Raw files→Ingest→Align→Clean→Exact-ID golden→Review candidates→Validate→Publish
1

Ingest: deserialize the source format

ingest_all_sources() walks RAW_FILES. A source-specific function turns CSV, JSON, Excel, or XML into a pandas DataFrame and attaches source_system.

Raw payroll example employee_id=3, source=AcquiredCo, base_salary=98952, currency=USD, pay_frequency=Bi-Weekly

No cross-source matching happens here. The goal is simply “bytes on disk → rows in memory + provenance.”

2

Align: translate source dialects into one schema

Each align_*_schema() function maps raw source fields into STANDARD_EMPLOYEE_COLUMNS. Missing concepts are explicitly filled with pd.NA.

Payroll aligned row employee_id=3 | company_origin=AcquiredCo salary_original=98952 | currency=USD | pay_frequency=Bi-Weekly first_name=<NA> | email=<NA> | source_system=payroll

This is an adapter layer. Once aligned, cleaning and deduplication do not need to know whether a record came from Excel or JSON.

Before a nonempty adapter runs, align_all_sources() checks its required raw columns. Missing columns now produce a source-specific ValueError; truly empty sources become empty canonical frames rather than crashing with KeyError.

3

Clean: make keys and values comparable

clean_standardized_dataframe() normalizes names, email, IDs, manager IDs, employment type, dates, salary, and departments.

ID normalization 3 + AcquiredCo → AC-000003 Salary normalization currently assumes 98952 × 1.00 USD rate × 26 biweekly periods = 2,572,752 USD/year

The ID result is intentional namespacing. The salary result is retained but later flagged because it exceeds $2 million—a useful example of why validation is separate from cleaning.

Checkpoint 1 — Why not “fix” the salary in cleaning?
Because the code does not have enough evidence to know whether the source amount or frequency label is wrong. Silently changing it would invent data. The safer current policy is to retain the transformed value, fail its business-range check, and send the source record for review.
4

Consolidate: build the identity spine, then enrich it

build_exact_id_golden_dataset() separates HRIS records from enrichment records. It deduplicates HRIS identities, finds enrichment IDs that have no HRIS identity, summarizes repeated payroll/benefit facts, and left-joins summaries onto HRIS.

  1. HRIS duplicate survivor: most populated identity row wins; source row order is the final deterministic tie-breaker.
  2. Payroll survivor: latest compensation effective date wins.
  3. Benefits summary: any enrollment means True; earliest date wins.
  4. Unmatched enrichment: exported as a ghost record, not a golden employee.
Golden AC-000003 now combines AcquiredCo HRIS identity + latest payroll compensation source_systems=acquiredco_hris|payroll dedup_method=exact_employee_id
5

Generate review candidates: detect possible cross-company identity overlap

Exact canonical IDs cannot join a pre-merger AcquiredCo identity to a GlobalTech identity because their namespaces deliberately differ. The pipeline therefore creates—not applies—two types of candidate link:

  • Same normalized full name and hire dates within 30 days.
  • RapidFuzz token_sort_ratio ≥ 88 and hire dates within 30 days.
Current review example AC-000038 Gary Phillips GT-008001 Larry Phillips score=88.888889 | hire-date gap=10 days | action=HR_REVIEW

The date window is a blocking rule: only plausible date neighbors get the more expensive name comparison. The score is evidence, not an employee key.

Checkpoint 2 — Why is a similarity score of 100 still review-only?
Because two real people can have exactly the same name and similar hire dates. A name score estimates string similarity, not identity truth. Email, date of birth, legal identifiers, or human confirmation would be needed for a safer merge decision.
6

Validate: measure contract compliance

DataQualityValidator runs 14 row-level masks. For every check it reports total, passed, failed, pass rate, and PASS/FAIL. Current output has one failed check type: 3,004 rows fail the annual salary range.

Gate semantics failed check types = 1 maximum allowed failed check types = 2 result: pipeline gate passes

This is subtle: employee-ID and company-origin checks are now critical, but the remaining gate still counts categories of failure rather than bad rows. A reviewer should ask whether failure-rate thresholds are also needed.

7

Publish: stabilize types and write consumer artifacts

prepare_for_parquet_export() coerces columns to predictable dtypes. write_golden_dataset() writes a staged Parquet dataset partitioned by company_origin, reads it back to verify the expected row count, and only then swaps it into place while retaining a temporary rollback backup. Exceptions go to CSV, validation also goes to HTML, and six charts go to PNG.

Partitioning produces company directories and allows company-filtered readers to skip irrelevant files. Parquet is columnar and typed, which is a better analytics contract than CSV.

The invariants to say aloud in review

  • Identity authority: only HRIS rows create golden employees.
  • Golden grain: exactly one row per canonical employee ID.
  • Key safety: company prefixes prevent cross-company numeric collisions.
  • Join safety: enrichment is summarized to one row per employee before joins.
  • Uncertainty policy: fuzzy identity evidence never mutates the golden dataset automatically.
  • Auditability: duplicate, ghost, probable-match, and failed-validation rows remain inspectable.

Verify the behavior yourself

From the repository root, run:

PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v

The nine tests exercise public behavior across cleaning, alignment, exact-ID integration, ghost isolation, duplicate review accuracy, critical validation gates, match exports, and staged publication. If unittest says tests is not importable, first check that your terminal is in the repository root and that you are using the project virtual environment.

Checkpoint — Why do we run with PYTHONPATH=src?
Because the importable hr_pipeline package lives under the repository's src/ directory. The environment value adds that directory to Python's module search path for the test run.

Final rehearsal

Scenario — A benefits record has employee ID GT-999999, but no HRIS record has that ID. Where does it go, and why?
It becomes a ghost enrichment record. It cannot enter golden because benefits is not an identity source, and the left-side identity spine contains only deduplicated HRIS employees.
Scenario — Two AcquiredCo HRIS rows normalize to AC-000123. Which one survives?
The row with more populated identity fields survives. If completeness and source system tie, stable source row order is the final tie-breaker. Both rows remain in the duplicate review output, but the internal row marker guarantees exactly one is marked kept_in_golden=True.
Scenario — Three noncritical quality check types fail, but only one row fails each. Does publishing continue?
No. assert_quality_gate raises when failed check types exceed two. Conversely, one check type may fail thousands of rows and still remain below the current gate.

Your 45-second review explanation

“This is a local batch pipeline that integrates two HRIS identity systems with payroll and benefits enrichment. Each raw format is ingested and adapted into a canonical schema, then common cleaning rules namespace IDs and standardize business fields. The golden identity spine is built only from HRIS, deduplicated deterministically, and enriched through exact IDs after payroll and benefits are reduced to one row per employee. Unmatched enrichment becomes ghost review data. Same-name and fuzzy matches are exported for HR review and never auto-merged. Fourteen checks validate the final grain and business rules, with critical identity checks failing immediately. A typed, company-partitioned Parquet dataset is staged, read back, and safely swapped into place before exception reports are published.”
